# BE-L01 · Стендовые данные — критерии приёмки (immutable)

Спека: workflow/specs/lobby-v2/BE-L01.md → docs/specs/lobby-v2/implementation.md#be-l01--стендовые-данные и «Правила для всех пакетов».
Критерии L01-01…L01-04: docs/specs/lobby-v2/acceptance.md#be-l01--стендовые-данные.
Контракты: docs/contracts/lobby-v2.md (для комнат приоритет), docs/contracts/discovery-v1.md, docs/contracts/mobile-api.md.
Зависимость: BE-D03 (PASS, workflow/reports/progress.md). Ветка `be-l01` от `dev`, база PR — `dev`.

Проверки выполняются через Nginx на изолированном стенде с dev-участниками `person1`…`person10`, одним посторонним и управляемым временем, по правилам docs/specs/lobby-v2/acceptance.md (шапка). Порядок карточек выводится из контракта (для EVENT — `startsAt, id`) и опубликованных данных стенда, без чтения реализации.

## Обязательные критерии

- **AC-01 (L01-01).** Вход под `person6`…`person10` завершается успешно, профили завершены, каталог и комнаты доступны. Повторный вход под `person1` на стенде с томами прежней сборки: `userId` участников 1–5 не изменились.
- **AC-02 (L01-02).** `GET /feed/candidates?kind=EVENT&localDate=2090-02-01` (все страницы курсора): ровно 35 карточек `dev-lobby-mix-01`…`dev-lobby-mix-35` по возрастанию номера; начало события N = `2090-02-01T00:00:00Z + N минут`; цена 1000 копеек; категория каждой карточки соответствует таблице BE-L01 (implementation.md, шаги 3):
  - 01–10 нечётные → `dev-lobby-a`; 01–10 чётные → `dev-lobby-b`;
  - 11, 14, 17, 20, 23, 26, 29, 32, 35 → `dev-lobby-a`;
  - 12, 15, 18, 21, 24, 27, 30, 33 → `dev-lobby-b`;
  - 13, 16, 19, 22, 25, 28, 31, 34 → `dev-lobby-c`.
- **AC-03 (L01-03).** Выдача `kind=EVENT&categoryId=dev-lobby-short` → ровно 4 карточки `dev-lobby-short-01`…`04` по возрастанию номера (начало `2090-03-01T00:00:00Z + N минут`); `kind=EVENT&categoryId=dev-lobby-two` → ровно 14 карточек `dev-lobby-two-01`…`14` по возрастанию номера (начало `2090-03-02T00:00:00Z + N минут`).
- **AC-04 (L01-04).** Повторный запуск Compose не создаёт дублей dev-данных; наборы `dev-swipe-places` и `dev-swipe-events` содержат по 22 карточки без дублей; INT-00 (docs/specs/discovery-v1/acceptance.md#29) выполняется: все сервисы готовы, миграции и dev-данные применены без дублей, регистрация/афиша/комнаты доступны через Nginx, PostgreSQL/Redis/Kafka не публикуют порты наружу.
- **AC-05 (Документация, implementation.md шаг 6).** README бэкенда описывает новых участников (`person6`…`person10`) и три набора: ID, категории, даты и фильтры выбора каждого набора (смешанный: `kind=EVENT&localDate=2090-02-01`; короткий: `kind=EVENT&categoryId=dev-lobby-short`; двухраундовый: `kind=EVENT&categoryId=dev-lobby-two`). Ссылки в README работают.

## Границы и регрессия (поведение API не меняется)

- **AC-06.** Правила для всех пакетов (implementation.md#правила-для-всех-пакетов): не изменены маршруты, статусы ошибок, приглашения, long polling, идемпотентность и одиночная выдача `GET /feed/candidates` (страницы по-прежнему 20 карточек); логика комнат и выдачи не менялась (проверяется по поведению: выдача `dev-swipe-events` = 20 + курсор, затем 2).
- **AC-07.** Существующие dev-наборы `dev-swipe-*` и `dev-vlad-*` и участники 1–5 не изменены (кроме добавления новых данных). Гарантии BE-D03 сохранены: одиночный проход комнаты на прежних данных ведёт себя как в Discovery v1.
- **AC-08.** Новый dev-участник-«посторонний» (по шапке acceptance.md комнаты v2) доступен для проверки изоляции комнат.
