# Спецификация разработки комнаты v2

Обязательное поведение описано в [контракте комнаты v2](../../contracts/lobby-v2.md). Применяются [архитектура, готовность, сопровождение контрактов и правила тестов](../../../workflow/rules/index.md). Основа — принятая реализация [BE-D03](../discovery-v1/implementation.md#be-d03--свайпы-на-одном-и-нескольких-устройствах).

Каждый пакет описан одинаково: цель, шаги, границы и условие готовности. Где именно менять код, разработчик читает в [памятке](developer-guide.md).

## Правила для всех пакетов

1. Делать только шаги своего пакета. Правила следующих пакетов не реализовывать заранее.
2. Менять только сервис swipes, его dev-данные и документацию. Каталог и identity меняет только BE-L01, и только в части dev-данных.
3. Не менять маршруты, статусы ошибок, приглашения, long polling, идемпотентность и одиночную выдачу `GET /feed/candidates`. Одиночная выдача по-прежнему отдаёт страницы по 20.
4. Не редактировать файлы тестировщика: `backend/services/matching/tests/`, `backend/services/catalog/tests/`, `backend/tests/` и `backend/tests/release-e2e/`. Если старый тест противоречит новому правилу, написать об этом в отчёте.
5. Сохранять гарантии BE-D03: один итог при параллельных завершениях, монотонная `version`, уведомление long polling после фиксации в PostgreSQL, состояние комнаты переживает перезапуск процесса.
6. В одном коммите с кодом обновлять документы, перечисленные в шагах пакета.
7. Перед отчётом выполнить проверки из [памятки](developer-guide.md#проверки-перед-отчётом).

## BE-L01 · Стендовые данные

**Цель.** Подготовить данные, на которых проверяются все следующие пакеты. Поведение API не меняется.

**Шаги.**

1. Добавить dev-участников `person6@example.test` … `person10@example.test` с завершённым профилем. ID и данные участников 1–5 не меняются.
2. Добавить три категории с типом `EVENT`: `dev-lobby-a`, `dev-lobby-b`, `dev-lobby-c`.
3. Добавить смешанный набор из 35 опубликованных событий `dev-lobby-mix-01` … `dev-lobby-mix-35`. Событие с номером N начинается `2090-02-01T00:00:00Z` плюс N минут. Цена 1000 копеек. Категории:

   | Номера | Категория |
   |---|---|
   | 01–10, нечётные | `dev-lobby-a` |
   | 01–10, чётные | `dev-lobby-b` |
   | 11, 14, 17, 20, 23, 26, 29, 32, 35 | `dev-lobby-a` |
   | 12, 15, 18, 21, 24, 27, 30, 33 | `dev-lobby-b` |
   | 13, 16, 19, 22, 25, 28, 31, 34 | `dev-lobby-c` |

4. Добавить категорию `dev-lobby-short` и 4 события `dev-lobby-short-01` … `04`, начало `2090-03-01T00:00:00Z` плюс N минут.
5. Добавить категорию `dev-lobby-two` и 14 событий `dev-lobby-two-01` … `14`, начало `2090-03-02T00:00:00Z` плюс N минут.
6. Описать участников и наборы в README бэкенда: ID, категории, даты и фильтры для выбора каждого набора.

**Как выбирать наборы.** Смешанный набор: `kind=EVENT&localDate=2090-02-01`. Короткий: `kind=EVENT&categoryId=dev-lobby-short`. Двухраундовый: `kind=EVENT&categoryId=dev-lobby-two`.

**Не трогать.** Код комнат и выдачи. Существующие наборы `dev-swipe-*` и `dev-vlad-*`.

**Готово, когда.** Выполнены L01-01 … L01-04. Повторный запуск Compose не создаёт дублей.

## BE-L02 · Пул из 10 и номер раунда

[Пул раунда](../../contracts/lobby-v2.md#пул-раунда) · [DTO](../../contracts/lobby-v2.md#dto)

**Цель.** Раунд комнаты содержит не больше 10 карточек и знает свой порядковый номер.

**Шаги.**

1. Ограничить пул раунда комнаты 10 карточками. Размер страницы одиночной выдачи остаётся 20.
2. Нумеровать раунды комнаты с 1. Добавить `number` в `Round`.
3. Обновить документы: `Round` в мобильном контракте, «Максимум 20 карточек в раунде» в Discovery v1, описание комнат в README бэкенда.

**Не трогать.** Правило матча, порядок карточек, срок комнаты, поведение при исчерпании.

**Готово, когда.** Выполнены L02-01 … L02-04.

## BE-L03 · Порог 70% и поля результата

[Порог матча](../../contracts/lobby-v2.md#порог-матча) · [DTO](../../contracts/lobby-v2.md#dto)

**Цель.** Матч требует лайков не меньше 70% состава, а результат объясняет, как он получен.

**Шаги.**

1. Создать модуль чистых функций правил комнаты и модульные тесты к нему. Подробности в памятке.
2. Заменить условие «лайков больше половины» на `likes * 10 >= memberCount * 7`. Считать только в целых числах.
3. Сохранить правило выбора: больше лайков, при равенстве более ранняя карточка пула.
4. При матче записывать `result = {winner, basis: "THRESHOLD", likes, memberCount}`.
5. Обновить документы: `Room.result` в мобильном контракте, правило большинства в Discovery v1 и в BE-04 спецификации бэкенда.

**Не трогать.** Порядок следующего пула, срок комнаты, поведение при исчерпании.

**Готово, когда.** Выполнены L03-01 … L03-05. Модульные тесты порога проходят.

## BE-L04 · Срок на каждый раунд

[Срок раунда](../../contracts/lobby-v2.md#срок-раунда)

**Цель.** Длинная сессия из нескольких раундов не обрывается, а зависший раунд закрывает комнату.

**Шаги.**

1. При создании каждого раунда задавать срок: момент создания плюс 30 минут.
2. Добавить `expiresAt` в `Round` в формате RFC 3339 UTC.
3. Закрывать комнату в `CLOSED`, когда истёк срок текущего раунда. Срок от старта первого раунда больше не используется.
4. Проверить, что срок раунда переживает перезапуск процесса и что long polling по-прежнему просыпается к сроку.
5. Обновить документы: `Round` в мобильном контракте, «Через 30 минут от старта первого раунда» в Discovery v1, описание часов стенда в README бэкенда.

**Не трогать.** Срок приглашения и срок курсора одиночной выдачи.

**Готово, когда.** Выполнены L04-01 … L04-04.

## BE-L05 · Следующий пул по весам категорий

[Следующий пул по весам](../../contracts/lobby-v2.md#следующий-пул-по-весам)

**Цель.** Каждый новый пул начинается с категорий, которые группе нравятся.

**Шаги.**

1. Сохранять итог каждого завершённого раунда: для каждой карточки её ссылку, категорию, число лайков и число пропусков. Сейчас голоса прошлого раунда теряются.
2. Добавить чистую функцию веса категорий: сумма `лайки − пропуски` по всем карточкам категории во всех завершённых раундах.
3. Добавить чистую функцию сортировки кандидатов: по убыванию веса категории, при равном весе в исходном порядке каталога. Категория без показов имеет вес 0.
4. При открытии следующего раунда действовать строго в таком порядке: убрать показанные карточки → отсортировать по весам → взять первые 10.
5. Написать модульные тесты обеих функций, включая пример из памятки.
6. Обновить документы: правило следующего пула в Discovery v1, BE-04 спецификации бэкенда и документацию swipes.

**Не трогать.** Порог матча, срок раунда, поведение при исчерпании.

**Готово, когда.** Выполнены L05-01 … L05-06. Модульные тесты весов проходят.

## BE-L06 · Итог по баллам при исчерпании

[Карточки закончились](../../contracts/lobby-v2.md#карточки-закончились)

**Цель.** Группа получает результат, если хоть кто-то что-то лайкнул.

**Шаги.**

1. Добавить чистую функцию выбора лидера по сохранённым итогам раундов: максимум лайков, при равенстве более ранний раунд, затем более ранняя карточка пула. Без единого лайка лидера нет.
2. Когда после раунда без матча непоказанных кандидатов нет: при наличии лидера перевести комнату в `MATCHED` с `result = {winner, basis: "TOP_SCORE", likes, memberCount}` и `round=null`. Без лидера — `EXHAUSTED`, `round=null`, `result=null`.
3. Пустой пул при старте по-прежнему даёт `EXHAUSTED`.
4. Написать модульные тесты выбора лидера.
5. Обновить документы: поведение при исчерпании в Discovery v1, BE-04 спецификации бэкенда, `Room.result` в мобильном контракте и документацию swipes.

**Не трогать.** Порог матча, сортировку пула, срок раунда.

**Готово, когда.** Выполнены L06-01 … L06-06. Модульные тесты лидера проходят.

## BE-L07 · Сверка документов и сквозной прогон

**Цель.** Документы описывают одно поведение, релиз проходит целиком.

**Шаги.**

1. Перенести правила комнаты v2 в раздел «Свайпы в комнате» Discovery v1 и убрать оттуда пометку о том, что стенд работает по прежним правилам.
2. Проверить, что в мобильном контракте, Discovery v1, спецификации бэкенда, документации swipes и README бэкенда нет прежних правил: 20 карточек в раунде комнаты, строгое большинство, срок от старта первого раунда.
3. Проверить ссылки между этими документами и контрактом комнаты v2.
4. Код менять только для исправления расхождений, найденных сквозным прогоном. Каждое такое исправление описать в отчёте.

**Не трогать.** Описание дизайна ленты.

**Готово, когда.** Выполнены L07-01 … L07-03.
